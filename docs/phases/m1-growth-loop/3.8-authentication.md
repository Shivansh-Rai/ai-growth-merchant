# Phase 3.8 — Authentication

**Status:** READY
**Milestone:** M1 Growth loop
**Requires:** 3.5, 3.6
**Unlocks:** 3.9

## Goal

Customers can register and log in on a storefront; merchants can log into the
dashboard; the two are separate namespaces; login triggers the identity
attribution backfill from 3.5.

## Authority

| Rule | Source |
|---|---|
| Actor boundaries — merchant, customer, AI worker | [ADR-2.7-007](../../architecture/phase-2.7-decisions.md#adr-27-007--domain-authorization-boundaries) |
| Login does not end the Session; sets `customerId` (immutable after) | [ADR-2.7-008](../../architecture/phase-2.7-decisions.md#adr-27-008--session-lifecycle-server-time) |

| No platform-admin actor | [ADR-2.8-009](../../architecture/phase-2.8-platform-decisions.md#adr-28-009--platform-boundaries-and-non-goals) |

## Scope note — minimal, but real

M1 needs authentication that genuinely gates commerce, not a complete account
system. **Real:** password hashing, server-side session verification, separate
namespaces, the attribution backfill. **Deferred:** password reset, email
verification, OAuth, remember-me, account settings, rate limiting on login.

This is a deliberate narrowing, recorded here so it is not mistaken for an
oversight.

### Migration

`passwordHash` is added **nullable** — the seed backfills it, and a NOT NULL
column against populated tables fails (the lesson from 3.4). Do not let Prisma
generate this one blind; check the SQL before applying.

## Contracts

```ts
// lib/auth/password.ts
export async function hashPassword(plain: string): Promise<string>;
export async function verifyPassword(plain: string, hash: string): Promise<boolean>;

// lib/auth/customer-session.ts
export type CustomerAuth = { customerId: string; storeId: string; sessionId: string };
/** Cookie is per-store, like the anonymous token (PLT-4). */
export function customerAuthCookieName(storeId: string): string;
export async function readCustomerAuth(storeId: string): Promise<CustomerAuth | null>;
export async function writeCustomerAuth(auth: CustomerAuth): Promise<void>;
export async function clearCustomerAuth(storeId: string): Promise<void>;

// lib/auth/register-customer.ts
export type RegisterCustomerInput = {
  storeId: string;
  sessionId: string;
  email: string;
  password: string;
  name?: string | null;
};
export async function registerCustomer(input: unknown): Promise<CustomerAuth>;

// lib/auth/login-customer.ts
/**
 * Verifies credentials, then attaches the customer to the RUNNING session —
 * login does not end it (ADR-2.7-008). The 3.5 backfill runs inside.
 */
export async function loginCustomer(input: unknown): Promise<{
  auth: CustomerAuth;
  attributedSessionCount: number;
}>;

// lib/auth/require-customer.ts
/**
 * The commerce gate (INV-10). Throws UNAUTHENTICATED when absent.
 * An anonymousId ALONE never satisfies this (ADR-2.7-010).
 */
export async function requireCustomer(storeId: string): Promise<CustomerAuth>;

// lib/auth/require-merchant.ts
export type MerchantAuth = { merchantId: string; storeId: string };
/** Dashboard gate. The ONLY way dashboard code learns its storeId (PLT-3). */
export async function requireMerchant(): Promise<MerchantAuth>;
```

### Login sequence (customer)

1. Resolve `storeId` from the route slug.
2. Look up Customer by `(storeId, email)`. **Same generic error** for unknown
   email and wrong password — do not leak which.
3. `verifyPassword`.
4. Resolve the current storefront Session from the anonymous cookie.
5. `attachCustomerToSession(storeId, sessionId, customerId)` — sets `customerId`
   and runs the backfill in one transaction.
6. Write the auth cookie. **Do not end the session and do not rotate the
   anonymous token** — rotating it would break the linkage the backfill just
   established.

## Invariants to enforce

| # | Rule | Enforced by |
|---|---|---|
| INV-7 | Merchant and Customer are separate namespaces | Separate tables, separate cookies, separate guards. A merchant cookie grants nothing on a storefront and vice versa |
| INV-5 | `customerId` immutable once set | `attachCustomerToSession` throws `CONFLICT` |
| INV-10 | Commerce requires a non-null `customerId`, verified server-side | `requireCustomer` at every commerce entry point, not a hidden button |
| ADR-2.7-010 | `anonymousId` is not an authorization credential | It is never consulted by `requireCustomer` |
| PLT-3 | `storeId` from route or authenticated merchant | Both guards return it; nothing else may |
| PRD-6 | Cost/margin stay merchant-only | Dashboard-only surfaces |

## Out of scope

Password reset, email verification, OAuth/social, remember-me, account settings,
merchant self-registration (seed only — [ADR-2.8-009](../../architecture/phase-2.8-platform-decisions.md#adr-28-009--platform-boundaries-and-non-goals)),
login rate limiting, CSRF hardening beyond same-site cookies.

Record any of these you feel the absence of as debt rows rather than building them.

Manual, against the running app:

| Check | Expected |
|---|---|
| Register on `/s/next-gen-electronics` | Customer created, logged in, session keeps its `customerId` |
| Browse anonymously, then log in | `attributedSessionCount >= 1`; prior anonymous sessions now carry `attributedCustomerId` |
| Same email on `/s/daily-dairy` | Succeeds — a separate Customer row. Store-scoped identity, by design |
| Customer cookie on a dashboard route | Rejected |
| Merchant cookie on a storefront commerce action | Rejected |
| Wrong password vs unknown email | **Identical** error message |
| Log in as a different customer in the same browser | New Session; the old one keeps its original `customerId` (INV-5) |
| Logout | Session `endedAt` set; auth cookie cleared |

Query the database after the backfill test and paste the affected Session rows,
showing `customerId` and `attributedCustomerId` side by side.

# Phase 3.10 — Checkout → Order (PENDING)

**Status:** DRAFT — expand to READY before implementing
**Milestone:** M1 Growth loop
**Requires:** 3.9
**Unlocks:** 3.11

## Goal

Checkout validates the cart server-side, calculates authoritative totals from
`Product`, and creates a PENDING Order whose items are an immutable purchase-time
snapshot.

## Scope

- `lib/checkout/start-checkout.ts` — validate → snapshot → create PENDING Order
- Server recalculates every price from `Product`. Nothing from the client.
- Re-validate at checkout: product in store, ACTIVE, purchasable, **sufficient
  stock right now** (a check, not a reservation)
- `OrderItem` rows snapshot `productName`, `sku`, `unitPricePaise`, `quantity`,
  `discountPaise`, `lineTotalPaise`
- `taxPaise`: computed for electronics (uniform 18%); null elsewhere — GST rates
  are not modelled ([ADR-2.8-009](../../architecture/phase-2.8-platform-decisions.md#adr-28-009--platform-boundaries-and-non-goals))
- Idempotency key on `(storeId, idempotencyKey)` — a double-submitted checkout
  returns the same Order, never a second one
- Emit `CHECKOUT_STARTED` with the order reference
- Order stores **no total**; Order Value is derived by summing lines
- `app/s/[storeSlug]/checkout/page.tsx` — review and confirm

## Decisions to make at expansion

1. **Cart state on checkout start.** The cart stays ACTIVE until payment
   succeeds (3.11 flips it to CONVERTED), since a PENDING order may never be
   paid — but confirm against ADR-2.7-015 and write it down.
2. **Multiple PENDING orders from one cart.** The schema allows it (`Order.cartId`
   nullable, no uniqueness). Decide whether to reuse the existing PENDING order
   or create another, and record the reasoning.
3. **Stock insufficient at checkout.** Reject the whole checkout, or drop the
   line and continue? Rejecting is simpler and more honest.

## Out of scope

Payment, inventory decrement, `PURCHASE` — all 3.11. Applied offers — 3.15.
Addresses, shipping, delivery slots — not in the MVP.

## Acceptance (sketch)

- Client-supplied prices and totals are ignored; server figures win
- Double-submit with the same idempotency key yields one Order
- `sum(lineTotalPaise)` equals the displayed Order Value
- Checkout with an out-of-stock line is rejected with a clear error
- Order is `PENDING`; no stock moved; no `PURCHASE` event exists

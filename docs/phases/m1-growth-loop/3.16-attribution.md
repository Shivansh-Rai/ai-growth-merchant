# Phase 3.16 — Attribution & Dashboard Figure

**Status:** DRAFT — expand to READY before implementing
**Milestone:** M1 Growth loop
**Requires:** 3.11, 3.15
**Unlocks:** 3.17

## Goal

When a PAID Order contains a product a customer was exposed to within 7 days, an
immutable `AttributionRecord` is written, and the merchant dashboard shows a real
attributed-revenue figure.

**This closes the loop.** After this phase the project does what its name says.

## Authority

| Rule | Source |
|---|---|
| Exposure required; 7-day window from `OFFER_VIEWED.receivedAt`; PAID orders only; last-touch 100%; amount = matched line total; immutable record; VOIDED on cancel; **causality never claimed** | [ADR-2.7-028](../../architecture/phase-2.7-decisions.md#adr-27-028--attribution-model-mvp) |

| Analytics = Postgres queries, no materialized metrics | [ADR-2.7-032](../../architecture/phase-2.7-decisions.md#adr-27-032--scalability-boundaries-not-built) |

## The rule, exactly

```text
for the PAID Order:
  find OFFER_VIEWED events for this customer, this store,
       receivedAt within 7 days before the order's paidAt
  keep those whose action's targetProductId appears as an OrderItem line
  → the MOST RECENT such exposure wins 100%      (last-touch)
  → amount = that matched line's lineTotalPaise  (GST-inclusive, counted once)
  → write ONE AttributionRecord; the partial unique index enforces one live
    record per Order
```

Identity linkage: prefer `AiAction.customerId`; else the Session's customer.
Anonymous exposure attributes **only** after identity resolution ties the Session
to a Customer *and* the Order's customer matches — otherwise no attribution. When
in doubt, attribute nothing.

## Scope

- `lib/growth/attribution/attribute-order.ts` — called after the Order reaches
  PAID, in the 3.11 confirmation path, **after commit**
- `lib/growth/attribution/void-attribution.ts` — Order CANCELLED → status
  `VOIDED`, `voidedAt` set. The record is never deleted or recalculated
- `ruleVersion` stamped on every record so a later rule change cannot rewrite history
- `AuditEntry(ATTRIBUTION_CREATED | ATTRIBUTION_VOIDED)`
- `lib/analytics/attributed-revenue.ts` — sum of non-VOIDED records for a store
  and period. A query, not a column
- Dashboard: wire `app/(dashboard)/overview` and `growth` to real figures

## Language — non-negotiable

The dashboard must say **"AI-attributed revenue"**, never "revenue generated by
AI", "AI-driven revenue", or "AI impact". Attributed revenue is measured under a
stated rule; it is not proof the AI caused the purchase (GR-12). Add a visible
one-line explanation of the rule next to the figure — a number whose definition
is hidden invites exactly the misreading the architecture spent four ADRs
avoiding.

The existing UI copy predates this. **Audit every growth and analytics string**
while wiring, not just the new ones.

## Decisions to make at expansion

1. **Cart-level actions.** ADR-2.7-028 says a cart-level action attributes if any
   line matches `targetProductId`. M1 has only `CROSS_SELL` with a single target,
   so confirm this is a no-op for now and note it.
2. **Multiple matching lines for one target.** The ADR says sum those lines once
   for the winning action. Only possible with duplicate product lines, which the
   `(cartId, productId)` uniqueness prevents. Confirm and note.
3. **`OrderItem.appliedActionId`.** Decide whether M1 populates it at checkout
   (ADR-2.7-023 fact #3) or leaves it null and relies purely on exposure
   matching. Leaving it null is simpler and sufficient for the M1 rule.
4. **Dashboard period.** What window the headline figure covers, and label it.

## Out of scope

Per-type attribution windows, multi-touch or fractional models, incremental or
causal measurement (explicitly out of scope forever without an experiment
design), refund-driven partial voids, cohort analysis.

## Acceptance (sketch)

Walk the full loop manually, then verify:

- Exposure → purchase of the target within 7 days → exactly one `AttributionRecord`
- Amount equals the matched `OrderItem.lineTotalPaise`
- **Purchase with no prior `OFFER_VIEWED` → no record.** Generation alone never attributes
- Exposure 8 days before purchase → no record
- Two exposures then one purchase → one record, credited to the **most recent**
- Cancelling the Order → record `VOIDED`, not deleted; the dashboard figure drops
- Dashboard figure equals the sum of non-VOIDED records, verified by SQL
- No dashboard string claims the AI *caused* anything
- `db:verify` still green on "no live AttributionRecord against a non-PAID order"

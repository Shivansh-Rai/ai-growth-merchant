# Phase 3.14 — Guardrail Engine & Frequency Ledger

**Status:** DRAFT — expand to READY before implementing
**Milestone:** M1 Growth loop
**Requires:** 3.13
**Unlocks:** 3.15

## Goal

A deterministic engine evaluates a `GENERATED` action against store Policies,
approves or rejects it with a reason, and writes an immutable evaluation
snapshot. Frequency limits are enforced by a unique constraint, not a read.

## Scope

- `lib/growth/guardrails/evaluate.ts` — the engine
- One checker per policy type, each pure and independently testable:
  `MAX_DISCOUNT`, `MIN_MARGIN`, `PRODUCT_ELIGIBILITY`, `CUSTOMER_ELIGIBILITY`,
  `FREQUENCY_LIMIT`, `INVENTORY_REQUIREMENT`
- **Structural checks that are not policies** and always run regardless of
  configuration: product in store, ACTIVE, purchasable, sufficient stock,
  candidate-set membership, action not expired
- `GuardrailEvaluation` row per pass with `phase`, `result`, `reason`, and a
  `rules` array recording each rule's policy id, type, **version** and outcome
- Frequency: insert into `FrequencyLedgerEntry`; a unique violation **is** the
  rejection. Never `SELECT` then `INSERT`
- `AiActionStatus`: `GENERATED → VALIDATING → APPROVED | REJECTED`
- `AuditEntry(AI_ACTION_APPROVED | AI_ACTION_REJECTED)`

### The headline demo case

The seeded data already contains it: the AI proposes 15%, the merchant's
`MAX_DISCOUNT` is 10%, the action is REJECTED with
*"Proposed discount of 15% exceeds the merchant maximum of 10%."* Once this
phase is real, that rejection is produced by the engine rather than written into
the seed. **Verify the engine reproduces it.**

### "Not configured" ≠ "passed"

When a store has no `MIN_MARGIN` policy, the snapshot must record that the
constraint was **not configured** — not that it passed. Merchant trust depends
on the difference, and a dashboard that shows "margin check: passed" for a rule
nobody set is lying.

## Decisions to make at expansion

1. **`MIN_MARGIN` when `costPricePaise` is null.** Cost is optional (PRD-5), so
   contribution is *unavailable*, not zero. Skip the check, or reject? Skipping
   is consistent with "unavailable is not zero" — but decide and record.
2. **Frequency bucket boundaries.** Hour buckets floored to the hour, or a
   rolling window? Floored is what the unique key expresses; a rolling window
   cannot be a unique constraint.
3. **Rejection visibility.** A rejected action stays auditable (GR-3) but is
   never rendered. Confirm nothing in 3.15 can read it.

## Out of scope

Merchant UI for editing policies — M2. Policy versioning UI. Execution-time
re-evaluation — that belongs to 3.15, where rendering happens.

## Acceptance (sketch)

- 5% proposed discount → APPROVED; 15% → REJECTED with the merchant's figure in the reason
- Evaluation snapshot records every rule touched **with its version**
- A store with no `MIN_MARGIN` policy records "not configured", not "passed"
- Two concurrent evaluations for the same `(customer, actionType, bucket)`:
  exactly one approved, the other rejected on the unique violation — **test it
  concurrently, not sequentially**
- A non-purchasable target is rejected even with zero policies configured
- Rejected actions keep their evaluation row

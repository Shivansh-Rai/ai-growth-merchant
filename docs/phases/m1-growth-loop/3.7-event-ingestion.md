# Phase 3.7 — Event Ingestion

**Status:** READY
**Milestone:** M1 Growth loop
**Requires:** 3.5, 3.6
**Unlocks:** 3.12, 3.15, 3.16

## Goal

Customer behaviour is recorded as immutable, per-type-validated Events with
server-authoritative timestamps, and the client can never create a `PURCHASE`.

## Contracts

```ts
// lib/events/payload-schemas.ts
/**
 * One schema per type. `.strict()` throughout — an unknown key is a bug in the
 * caller, not something to silently accept (EV-10).
 */
export const EVENT_PAYLOAD_SCHEMAS: Record<EventType, z.ZodTypeAny>;

/** Types a browser is allowed to submit. PURCHASE is deliberately absent. */
export const CLIENT_SUBMITTABLE: ReadonlySet<EventType>;

// lib/events/record-event.ts
export type RecordEventInput = {
  storeId: string;
  sessionId: string;
  type: EventType;
  payload: unknown;
  /** Untrusted client claim, retained for analytics only. */
  clientOccurredAt?: string | null;
  /** Optional soft-dedupe key, unique per (sessionId, clientEventId). */
  clientEventId?: string | null;
  /** OFFER_* only. */
  aiActionId?: string | null;
  /** CHECKOUT_STARTED only; PURCHASE goes through recordPurchase. */
  orderId?: string | null;
};
export async function recordEvent(input: unknown): Promise<Event>;

// lib/events/record-purchase.ts
/**
 * The ONLY way a PURCHASE Event is created (ADR-2.7-011). Called from the
 * payment confirmation path in 3.11, after the Order reaches PAID — never from
 * an HTTP handler reachable by a browser.
 */
export async function recordPurchaseEvent(args: {
  storeId: string;
  sessionId: string;
  orderId: string;
  orderValuePaise: number;
  itemCount: number;
}): Promise<Event>;
```

### Payload shapes

From [activity-tracking §5.5](../../architecture/activity-tracking.md). Keep them
minimal — an Event payload holds only what that event needs (EV-10).

| Type | Payload |
|---|---|
| `SEARCH` | `{ query: string; resultCount: number }` |
| `PRODUCT_VIEW` | `{ productId: string }` |
| `PRODUCT_CLICK` | `{ productId: string; source: "SEARCH" \| "CATEGORY" \| "AI_ACTION" \| "RELATED" }` |
| `ADD_TO_CART` | `{ cartId: string; productId: string; quantity: number; observedPricePaise: number }` |
| `REMOVE_FROM_CART` | `{ cartId: string; productId: string; quantity: number }` |
| `CART_VIEW` | `{ cartId: string; itemCount: number }` |
| `CHECKOUT_STARTED` | `{ cartId: string; cartValuePaise: number }` |
| `OFFER_VIEWED` / `OFFER_CLICKED` / `OFFER_DISMISSED` | `{ surface: Surface; actionType?: AiActionType; offerId?: string }` |
| `PURCHASE` | `{ orderId: string; orderValuePaise: number; itemCount: number }` |

`observedPricePaise` on `ADD_TO_CART` is **behavioural evidence, not financial
truth** — it is why `CartItem` stores no price (ADR-2.7-015).

### The API route

```
POST /api/s/[storeSlug]/events
```

In order:

1. Resolve `storeId` from the **route slug** (PLT-3). Ignore any `storeId` in the body.
2. Resolve the Session from the per-store cookie. Reject if it does not belong to this store.
3. Reject `type` not in `CLIENT_SUBMITTABLE` with **403** and a clear message.
4. Validate the payload against that type's schema.
5. `recordEvent`, then `touchSession`.
6. Return `202` with `{ id }`. Telemetry failures must never break a page.

## Invariants to enforce

| # | Rule | Enforced by |
|---|---|---|
| EV-1 | Every Event belongs to exactly one Session | `sessionId` required, composite FK |
| EV-2/3 | Immutable; never moved between Sessions | No update or delete path exists anywhere |
| ADR-2.7-011 | Client cannot create `PURCHASE` | `CLIENT_SUBMITTABLE` excludes it; route returns 403 |
| ADR-2.7-012 | `receivedAt` is server time | Never settable from input |
| ADR-2.7-007 | Payload ≤ 16 KiB | Check in the service so it fails cleanly before the DB CHECK |
| ADR-2.7-011 | `OFFER_*` requires `aiActionId` | Schema + existing DB CHECK |
| EV-6 | Taxonomy stays small | No new `EventType` values in this phase |

## Out of scope

- Emitting `ADD_TO_CART` / `CHECKOUT_STARTED` — phases 3.9, 3.10 call `recordEvent`
- Emitting `OFFER_*` — phase 3.15
- Calling `recordPurchaseEvent` — phase 3.11
- Retention sweeps, analytics queries, dashboards
- Batching or an outbox — one row per request is correct at this scale

## Acceptance

```bash
npx tsc --noEmit
npm run lint
npm run db:verify
```

Against the running app:

```bash
# 1. Valid telemetry -> 202
curl -i -X POST localhost:3000/api/s/next-gen-electronics/events \
  -H 'content-type: application/json' \
  -b cookies.txt \
  -d '{"type":"PRODUCT_VIEW","payload":{"productId":"seed_prod_vtx_rpd1tb"}}'

# 2. Client-submitted PURCHASE -> 403
curl -i -X POST localhost:3000/api/s/next-gen-electronics/events \
  -H 'content-type: application/json' -b cookies.txt \
  -d '{"type":"PURCHASE","payload":{"orderId":"x","orderValuePaise":1,"itemCount":1}}'

# 3. Unknown payload key -> 400
curl -i -X POST localhost:3000/api/s/next-gen-electronics/events \
  -H 'content-type: application/json' -b cookies.txt \
  -d '{"type":"PRODUCT_VIEW","payload":{"productId":"x","evil":true}}'

# 4. storeId in the body is ignored, not honoured
curl -i -X POST localhost:3000/api/s/next-gen-electronics/events \
  -H 'content-type: application/json' -b cookies.txt \
  -d '{"storeId":"dairy_store_daily","type":"PRODUCT_VIEW","payload":{"productId":"seed_prod_vtx_rpd1tb"}}'
```

Expected: `202`, `403`, `400`, `202` — and for (4), the stored row's `storeId`
must be the **electronics** store. Paste the four responses and the row.

Browsing a product detail page must produce exactly one `PRODUCT_VIEW`.

New `db:verify` assertions: no Event with a null `sessionId`; every `OFFER_*`
carries an `aiActionId`; no Event's `storeId` differs from its Session's.

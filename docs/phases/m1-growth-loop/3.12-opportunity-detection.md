# Phase 3.12 — Opportunity Detection

**Status:** DRAFT — expand to READY before implementing
**Milestone:** M1 Growth loop
**Requires:** 3.9, 3.11
**Unlocks:** 3.13

## Goal

A deterministic rule reads Events and cart state and creates an `Opportunity`.
**No model is involved in this phase.**

## Authority

| Rule | Source |
|---|---|
| Deterministic signals → Opportunity; the LLM does not rediscover database facts; lifecycle, dedupe key, 24h TTL | [ADR-2.7-024](../../architecture/phase-2.7-decisions.md#adr-27-024--opportunity-model) |
| Opportunity ≠ AI Action; an opportunity may exist with no action | [growth §6](../../architecture/growth-system-and-guardrails.md), AI-5 |
| Only catalog-supported relations | [ADR-2.7-025](../../architecture/phase-2.7-decisions.md#adr-27-025--ai-action-lifecycle--output-boundary) |

## The one rule for M1

**GPU in cart, no PSU in cart, compatible PSU in stock → `CROSS_SELL` opportunity.**

This rule is chosen because it is entirely catalog-supported: the GPU's
`recommendedPsuWatts` spec and the PSU's `wattage` spec make compatibility a
*join*, not an inference. The seeded electronics catalogue already contains the
data (`seed_prod_vtx_rtx4070` → `seed_prod_vtx_srg750`).

That matters: ADR-2.7-025 rules out AI-inferred compatibility without catalog
support. The rule must read specs, not guess.

## Scope

- `lib/growth/opportunities/detect-cross-sell-psu.ts` — the rule
- `lib/growth/opportunities/create-opportunity.ts` — dedupe-safe writer
- `evidence` JSON: the Event ids and Product ids that justify it — structured
  references, not prose
- `dedupeKey`: stable per `(customerId, anchorProductId, type)` so re-running
  detection does not create duplicates. The partial unique index on OPEN
  opportunities is the arbiter
- `expiresAt`: `now() + 24h`
- Trigger: called after `ADD_TO_CART`. Synchronous is fine — no queue, no worker
  ([ADR-2.7-032](../../architecture/phase-2.7-decisions.md#adr-27-032--scalability-boundaries-not-built))

## Decisions to make at expansion

1. **Where detection is invoked.** After the `ADD_TO_CART` event write, inside
   or outside that request's transaction. Outside is safer — a detection bug
   must not roll back a customer's cart.
2. **Resolution.** ADR-2.7-024 says an Opportunity resolves when its Action
   executes, a merchant suppresses it, it expires, or it becomes ineligible.
   Decide which of these 3.12 owns versus 3.15.
3. **Anonymous customers.** `Opportunity.customerId` is nullable, but cart
   requires auth, so this rule always has one. Confirm and note it.

## Out of scope

Any model call — 3.13. Guardrails — 3.14. Rendering — 3.15. More rules,
abandoned-checkout detection, background sweeps — M2.

## Acceptance (sketch)

- Adding the seeded GPU to a cart with no PSU creates exactly one OPEN opportunity
- Adding it again creates **no** second opportunity (dedupe holds)
- Adding a PSU first, then the GPU, creates **no** opportunity
- The rule finds the PSU by spec join, not by hardcoded product id
- `evidence` references real Event and Product ids
- Opportunity carries the correct `storeId`; the same cart shape in another store does not leak

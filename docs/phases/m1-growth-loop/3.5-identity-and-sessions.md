# Phase 3.5 — Identity & Sessions

**Status:** READY
**Milestone:** M1 Growth loop
**Requires:** 3.4
**Unlocks:** 3.6, 3.7, 3.8

## Goal

The server can create store-scoped Customers, open and maintain Sessions with
per-store anonymous tokens, and atomically back-fill identity attribution when a
customer logs in.

| Rule | Source |

## Contracts

```ts
// lib/identity/errors.ts
export type IdentityErrorCode = "VALIDATION" | "NOT_FOUND" | "CONFLICT";
export class IdentityDomainError extends Error {
  constructor(code: IdentityErrorCode, message: string, meta?: { field?: string });
}

// lib/identity/anonymous-id.ts
/** 128 bits of crypto randomness, base64url. Server-side only. */
export function mintAnonymousId(): string;

// lib/identity/create-customer.ts
export type CreateCustomerInput = {
  storeId: string;
  email: string;
  name?: string | null;
  phone?: string | null;
};
export async function createCustomer(input: unknown): Promise<Customer>;

// lib/identity/get-customer.ts
export async function getCustomerByEmail(
  storeId: string,
  email: string,
): Promise<Customer | null>;
export async function getCustomer(storeId: string, customerId: string): Promise<Customer | null>;

// lib/identity/start-session.ts
export type StartSessionInput = {
  storeId: string;
  /** Existing per-store token from the cookie, or null to mint a new one. */
  anonymousId?: string | null;
};
/** Always creates a NEW Session row. Reuses the token when one is supplied. */
export async function startSession(input: unknown): Promise<Session>;

// lib/identity/touch-session.ts
/** Bumps lastActivityAt to server now(). No-op if the session has ended. */
export async function touchSession(storeId: string, sessionId: string): Promise<void>;

// lib/identity/end-session.ts
/** Explicit logout only. Idempotent: ending an ended session is a no-op. */
export async function endSession(storeId: string, sessionId: string): Promise<void>;

// lib/identity/session-state.ts
export type SessionState = "ACTIVE" | "ENDED";
/** DERIVED, never stored: endedAt set, or now - lastActivityAt > 30 min. */
export function sessionState(
  session: Pick<Session, "endedAt" | "lastActivityAt">,
  now?: Date,
): SessionState;
export const SESSION_INACTIVITY_MS: number; // 30 * 60 * 1000

// lib/identity/attach-customer.ts
export type AttachCustomerResult = {
  session: Session;
  /** Prior anonymous sessions claimed by the backfill. */
  attributedSessionCount: number;
};
/**
 * Login. Sets customerId on the running session (never overwrites — INV-5),
 * then runs the ADR-2.7-009 backfill in the same transaction.
 */
export async function attachCustomerToSession(
  storeId: string,
  sessionId: string,
  customerId: string,
): Promise<AttachCustomerResult>;
```

### The backfill

Exactly this, inside the same transaction as the `customerId` write. Do not
re-derive it:

```sql
UPDATE "sessions"
SET "attributedCustomerId" = $1
WHERE "anonymousId" = $2
  AND "storeId" = $3
  AND "startedAt" >= $4          -- now() - 30 days
  AND "customerId" IS NULL
  AND "attributedCustomerId" IS NULL
```

Use `$executeRaw` — Prisma's `updateMany` cannot express "first claim wins"
atomically here. Every guard is load-bearing:

| Guard | Defends against |
|---|---|
| `storeId` match | Cross-store identity leakage |
| `customerId IS NULL` | Reassigning a session someone else was logged into |
| `attributedCustomerId IS NULL` | Two people on one device stealing each other's history |
| 30-day window | Indefinite retention of pre-login behaviour |

## Invariants to enforce

| # | Rule | Enforced by |
|---|---|---|
| INV-2 | Customer belongs to exactly one Store | `(storeId, email)` unique + explicit `storeId` |
| INV-4 | Every Session has non-null `anonymousId`; `customerId` nullable | Schema |
| INV-5 | `customerId`, once set, never changes to a different Customer | **Application** — throw `CONFLICT` if already set to a different id. PostgreSQL cannot express this without a trigger, which Phase 3 does not introduce |
| INV-8 | `attributedCustomerId` only on a Session whose `customerId` is null | CHECK + the backfill's `WHERE` |
| INV-9 | Attribution never modifies or deletes an Event | No Event writes in this phase at all |
| PLT-4 | Never query `anonymousId` without `storeId` | Every query in this phase |
| ADR-2.7-008 | Session end is derived, never stored | `sessionState()`; no status column |

## Out of scope

- HTTP routes, cookies, middleware — phase 3.6
- Passwords, credentials, login UI — phase 3.8
- Any Event write — phase 3.7
- Merchant authentication — phase 3.8
- Session "resume": `startSession` always creates a row. Deciding whether to
  resume or open a new one is the caller's job in 3.6

## Acceptance

Add to `scripts/verify-db.ts` a `checkIdentity()` section asserting:

- no Session has `attributedCustomerId` set while `customerId` is non-null (INV-8)
- no Session has a null or empty `anonymousId` (INV-4)
- no `anonymousId` appears under two `storeId`s (PLT-4 — already present, keep)

Then write `scripts/_check-identity.ts` as a throwaway harness proving the
behaviour, and paste its output into the phase report:

```bash
npx tsc --noEmit
npm run lint
npm run db:verify
npx tsx --env-file=.env scripts/_check-identity.ts
```

The harness must demonstrate, against the seeded `next-gen-electronics` store:

1. `startSession` with no token mints a fresh `anonymousId`; two calls give
   different tokens.
2. `startSession` with an existing token reuses it and creates a second Session
   row.
3. `sessionState` returns `ENDED` for a session whose `lastActivityAt` is 31
   minutes old, and `ACTIVE` at 29 minutes.
4. `attachCustomerToSession` sets `customerId` and reports
   `attributedSessionCount >= 1` for a prior anonymous session on the same token.
5. **Running it twice attributes the second time zero** — first claim wins.
6. A second `attachCustomerToSession` with a *different* `customerId` throws
   `CONFLICT` (INV-5).
7. A session belonging to `daily-dairy` is untouched by a login in
   `next-gen-electronics`.

Delete the harness before committing; keep its output in the report.

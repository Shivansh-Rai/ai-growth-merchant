# Phase 3.11 — Payment, Inventory Decrement, PURCHASE

**Status:** DRAFT — expand to READY before implementing
**Milestone:** M1 Growth loop
**Requires:** 3.10
**Unlocks:** 3.16

> **This is the most correctness-sensitive phase in the project.** It is also
> where two of the portfolio's best interview stories stop being designs and
> start being code that has actually run. Budget time for the tests, not just
> the happy path.

## Goal

A verified Razorpay test payment atomically decrements inventory and moves the
Order to PAID, emits the server-side `PURCHASE`, and is safe under duplicate
webhooks and concurrent buyers of the last unit.

## The sequence — do not reorder

```text
create PaymentAttempt (PENDING) ─→ Razorpay order        [outside any txn]
                                          ↓
                             browser completes payment
                                          ↓
                          webhook arrives → verify signature
                                          ↓
                      already processed for this providerEventId? → no-op
                                          ↓
┌─ BEGIN TRANSACTION ─────────────────────────────────────────────┐
│  order already PAID?  → commit, no-op (duplicate webhook)       │
│  for each line:                                                 │
│    UPDATE products SET "stockQuantity" = "stockQuantity" - :qty │
│    WHERE "id" = :id AND "storeId" = :storeId                    │
│      AND "stockQuantity" >= :qty                                │
│      AND "lifecycleStatus" = 'ACTIVE'                           │
│    → 0 rows affected?  ABORT THE WHOLE TRANSACTION              │
│  PaymentAttempt → SUCCEEDED                                     │
│  Order → PAID, paidAt = now()                                   │
│  Cart → CONVERTED                                               │
└─ COMMIT ────────────────────────────────────────────────────────┘
                                          ↓
                          recordPurchaseEvent()   [after commit]
                                          ↓
                                AuditEntry(PAYMENT_CONFIRMED)
```

**Fail closed.** If the decrement cannot be satisfied, the Order does **not**
become PAID and no `PURCHASE` is emitted, even though the money was taken
externally. That is a reconciliation problem for a human, not something to paper
over by marking the order paid anyway (ADR-2.7-019).

Never call Razorpay from inside the transaction — an external call holding a
database transaction open is how connection pools die.

## Scope

- `lib/payments/` — create attempt, verify webhook signature, confirm
- `app/api/webhooks/razorpay/route.ts` — one endpoint for **all** stores;
  `providerPaymentId` is globally unique and its row carries `storeId`, so no
  per-store routing is needed
- Razorpay test-mode client; secrets from env, never committed
- `AuditEntry(PAYMENT_CONFIRMED)`
- Order confirmation page

## Decisions to make at expansion

1. **Stock conflict after external success.** ADR-2.7-019 offers a
   `SUCCEEDED_STOCK_CONFLICT` marker or fail-closed-and-alert. `PaymentAttemptStatus`
   has no such value today, so either use `failureReason` on a `SUCCEEDED`
   attempt with the Order left PENDING, or raise an ADR to add the status.
   **Do not add an enum value without recording it.**
2. **Webhook vs client callback.** The browser callback may arrive first. Decide
   whether it can trigger confirmation at all, or whether only the webhook may —
   the browser is never authoritative (CO-11).
3. **Local webhook delivery.** ngrok, the Razorpay CLI, or a test harness that
   posts a signed payload directly. The last is cheapest and is enough to prove
   idempotency.

## Tests — required, not optional

This phase introduces the first test runner (debt D-11). Two tests matter more
than broad coverage:

**Concurrent buyers of the last unit.** Set a product to `stockQuantity = 1`,
fire two confirmations concurrently. Exactly one Order reaches PAID; the other
fails closed. Stock ends at 0, never negative.

**Duplicate webhook.** Deliver the same `providerEventId` five times. Stock
decrements once, one `PURCHASE` event exists, the Order is PAID, and attempts
four and five are no-ops.

These are the two stories you will be asked about in an interview. Make them
real and keep the output.

## Out of scope

Refunds, chargebacks, partial payments, settlement, payouts, commission
(ADR-2.8-009). Retry UI beyond a second attempt on the same Order.

## Acceptance (sketch)

- End-to-end test payment succeeds; Order PAID, stock down, `PURCHASE` present, cart CONVERTED
- Both concurrency tests pass, output pasted
- Unsigned or wrongly-signed webhook rejected
- Failed payment produces no `PURCHASE` and no stock movement (CO-12)
- `db:verify` still green, including "no PURCHASE for a non-PAID order"
- No Razorpay call occurs inside a transaction — state how this was verified
